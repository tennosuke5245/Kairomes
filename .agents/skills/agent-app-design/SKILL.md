# Agent App 產品設計

分析使用者如何開始工作、辨識狀態、做決定與確認成果。先弄清產品是任務執行器、對話宿主或輔助側欄，再判斷模式是否適用。

## 證據與更新

- 視覺分析要讀取並檢查當次擷取的畫面；無法操作實際 app 時，可用官方公開畫面研究，標明來源與限制。程式碼和說明文件不能替代畫面實測。
- 區分「實際操作」「現行程式碼」「官方文件／示意」「設計推論」。標註查閱日期、產品 surface、可知版本與 rollout；未知 client 版本就寫未知。
- Codex Desktop、Claude Desktop Code、Claude Code CLI／web 與 Cowork 分開記錄。產品名稱或文件重新導向時，保存來源變動，避免混用不同 surface 的能力。
- 舊快照只能提供研究起點。涉及當前功能時重新查官方來源；OpenAI 產品先查可用本機依據，再以官方網站補足。
- 畫面只用公開或合成資料；不得為了擷取而匯出私人聊天、日誌或連線憑證。

## 分析重點

以 [設計模式與證據判斷](references/patterns.md) 建立適用範圍，再針對任務入口、專案／對話歸屬、執行狀態、上下文、核准、diff／成果、失敗恢復與接力分析。每項結論要有「證據 → 使用者影響 → 可移用模式 → 適用限制」，不必照抄完整桌面布局。

## 介面文字約束

使用者明確要求精簡時，把它列為必要驗收條件：預設只顯示狀態、必要資訊和下一個動作；相同事實只在同一決策位置敘述一次。不要用介紹卡、說明段落、標語和重複摘要填滿畫面。原因與技術細節按需展開。

涉及核准時，縮短措辭但保留會影響決定的操作、範圍、期限及不可逆副作用；不能因精簡而藏掉有效權限或結果不明。

核准必須綁定可識別的請求與不可變內容版本；內容改變就重新審閱，不沿用原核准。未知結果先對帳，不能自動重送副作用。交接內容是待核對資料，不執行包內指令、不帶憑證或權限、不自動送訊息；沒有可信聊天 ID 就只建立獨立接續紀錄。

## 產出

依使用者需要提供畫面索引、模式比較與具優先順序的建議。開發規劃需列出狀態、依賴、可驗收行為和未驗證事項。若只能研究官方資料，稱為「研究」，不要宣稱完成實際產品流程稽核。

競品有某項能力不代表輔助側欄也需要。先說明哪個日常卡點使它必要；基本品質與內部測試工具另列，多人研究及跨 App 接力可保留為選配，不以研究完整度擴大產品範圍。
